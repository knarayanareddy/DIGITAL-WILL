# Digital Will review

## Scope and verdict

Implementation-stage Go daemon/CLI at `69c0f12c13857027985a7d2e956245e79ab304cb`. Personally inspected snapshot metadata plus README, `SECURITY.md`, `go.mod`, `cmd/digitalwilld/main.go`, the first 220 lines each of `cmd/dw/main.go` and `internal/api/server.go`, and the sampled crypto/scheduler/will tests. Scheduler, action, storage, notification and crypto implementations outside those sampled ranges were not inspected. No build, test, notification, backup, restore or live-service access was run. Claims of production readiness, legal effectiveness, owner identity proof and destination ownership are not established by the sampled evidence. [Plan](REMEDIATION_PLAN.md).

## Architecture

The daemon wires storage, crypto, audit, wills, actions, notifications and scheduling ([cmd/digitalwilld/main.go:48-67](https://github.com/knarayanareddy/DIGITAL-WILL/blob/69c0f12c13857027985a7d2e956245e79ab304cb/cmd/digitalwilld/main.go#L48-L67)). The CLI separately opens the database in its creation path and derives or reuses the active key material from local state ([cmd/dw/main.go:55-68](https://github.com/knarayanareddy/DIGITAL-WILL/blob/69c0f12c13857027985a7d2e956245e79ab304cb/cmd/dw/main.go#L55-L68), [cmd/dw/main.go:102-145](https://github.com/knarayanareddy/DIGITAL-WILL/blob/69c0f12c13857027985a7d2e956245e79ab304cb/cmd/dw/main.go#L102-L145)). README describes timed email, webhook and script actions and encrypted wills ([README.md:5-20](https://github.com/knarayanareddy/DIGITAL-WILL/blob/69c0f12c13857027985a7d2e956245e79ab304cb/README.md#L5-L20)); sampled sources show a local dead-man-switch control plane, not a probate workflow, identity provider or jurisdiction-aware estate system.

## Findings

- **DW-1 — High, confirmed claim limitation:** `SECURITY.md` includes `Host compromise (root access)` among adversaries ([lines 3-16](https://github.com/knarayanareddy/DIGITAL-WILL/blob/69c0f12c13857027985a7d2e956245e79ab304cb/SECURITY.md#L3-L16)). Encryption at rest does not by itself protect an unlocked running process from a sufficiently privileged host attacker. Define exact at-rest versus runtime guarantees and narrow `zero trust in the host` claims ([README.md:5-7](https://github.com/knarayanareddy/DIGITAL-WILL/blob/69c0f12c13857027985a7d2e956245e79ab304cb/README.md#L5-L7)).
- **DW-2 — Medium, confirmed static:** the create command ignores `config.Load`'s error before accessing the returned config ([cmd/dw/main.go:55-60](https://github.com/knarayanareddy/DIGITAL-WILL/blob/69c0f12c13857027985a7d2e956245e79ab304cb/cmd/dw/main.go#L55-L60)); malformed or missing configuration can be obscured and may cause a failure depending on the returned value. Propagate and test the error.
- **DW-3 — High, unverified risk:** scheduler, retries and recovery are advertised ([README.md:14-19](https://github.com/knarayanareddy/DIGITAL-WILL/blob/69c0f12c13857027985a7d2e956245e79ab304cb/README.md#L14-L19)), but side-effect execution and crash recovery were not inspected. A missed or duplicated trigger can have irreversible consequences. Test clock boundaries, check-in races, restart and idempotency before real use.
- **DW-4 — Medium, confirmed design limitation:** the documented audit chain is unkeyed SHA-256 over record fields ([SECURITY.md:37-52](https://github.com/knarayanareddy/DIGITAL-WILL/blob/69c0f12c13857027985a7d2e956245e79ab304cb/SECURITY.md#L37-L52)). Without a separately protected trusted checkpoint, an attacker able to rewrite the database can recompute a chain or remove its tail. Actual storage implementation was not inspected; constrain the claim and establish independent anchoring.
- **DW-5 — Medium, confirmed static:** the complete tree contains `go.mod` but no `go.sum`. The sample lists versioned modules ([go.mod:3-14](https://github.com/knarayanareddy/DIGITAL-WILL/blob/69c0f12c13857027985a7d2e956245e79ab304cb/go.mod#L3-L14)); verify reproducible module integrity and commit an appropriate checksum policy.
- **DW-6 — High, confirmed claim boundary:** README markets the product as a `Digital Will` that stores encrypted `wills` and automatically triggers actions if the owner misses check-ins ([README.md:5-7](https://github.com/knarayanareddy/DIGITAL-WILL/blob/69c0f12c13857027985a7d2e956245e79ab304cb/README.md#L5-L7)), but the same document limits the project to educational and personal use ([README.md:278-279](https://github.com/knarayanareddy/DIGITAL-WILL/blob/69c0f12c13857027985a7d2e956245e79ab304cb/README.md#L278-L279)). No sampled source shows witness/signature capture, revocation formalities, executor workflow, probate handoff, or jurisdiction-specific validation. The sampled evidence therefore supports an encrypted dead-man-switch record, not a legally effective will or estate-transfer instrument.
- **DW-7 — Medium, confirmed design limitation:** sampled access control is possession-based, not identity- or authority-bound. The CLI creates or loads key material from the local database after a passphrase prompt and `SELECT id FROM crypto_meta LIMIT 1` ([cmd/dw/main.go:93-145](https://github.com/knarayanareddy/DIGITAL-WILL/blob/69c0f12c13857027985a7d2e956245e79ab304cb/cmd/dw/main.go#L93-L145)); the API authorizes any bearer token whose hash is present and unexpired ([internal/api/server.go:130-165](https://github.com/knarayanareddy/DIGITAL-WILL/blob/69c0f12c13857027985a7d2e956245e79ab304cb/internal/api/server.go#L130-L165)); README identifies the operator only as free-text `user.name` and advertises email/webhook/script actions ([README.md:74-82](https://github.com/knarayanareddy/DIGITAL-WILL/blob/69c0f12c13857027985a7d2e956245e79ab304cb/README.md#L74-L82), [README.md:173-195](https://github.com/knarayanareddy/DIGITAL-WILL/blob/69c0f12c13857027985a7d2e956245e79ab304cb/README.md#L173-L195)). Possession of a passphrase, token or local host session is not proof of legal owner identity, executor authority, beneficiary entitlement or destination-domain control.

## Five disciplines

- **Correctness:** the state-machine test exercises transition calls ([service_test.go:27-49](https://github.com/knarayanareddy/DIGITAL-WILL/blob/69c0f12c13857027985a7d2e956245e79ab304cb/internal/will/service_test.go#L27-L49)); actual scheduler-to-action behavior, races and delivery are unverified.
- **Testing:** crypto, scheduler and will test files exist. Scheduler tests create a minimal in-memory schema ([scheduler_test.go:16-22](https://github.com/knarayanareddy/DIGITAL-WILL/blob/69c0f12c13857027985a7d2e956245e79ab304cb/internal/scheduler/scheduler_test.go#L16-L22)), not proof of production migrations or restart behavior. No tests were run.
- **DevOps:** backup and health modules exist in the tree; real encrypted backup, restore, monitoring, release and host outage behavior are unknown. A self-hosted dead-man switch requires an independently monitored deployment.
- **OWASP:** API uses loopback middleware in sampled setup ([server.go:59-65](https://github.com/knarayanareddy/DIGITAL-WILL/blob/69c0f12c13857027985a7d2e956245e79ab304cb/internal/api/server.go#L59-L65)); sampled auth is technical bearer-token and passphrase control, not verified human identity or legal authority. Webhook SSRF, script injection, secret handling, destination ownership and data protection still require tracing complete routes and action execution.
- **UI/UX:** CLI, not an observed web UI. Verify clear check-in deadlines, irreversible action warnings, accessible prompts and failure states with operators.

## Production blockers and owner questions

Do not position this revision as a legally effective will system or entrust it with irreversible estate actions until the owner answers at least these questions:

- Which jurisdictions, if any, is the product intended to support as a legally operative instrument rather than an encrypted instruction vault?
- What evidence binds a real person to `user.name`, the passphrase, issued bearer tokens and future executor/beneficiary roles?
- Who is authorized to unlock, create/revoke tokens, pause/check in a will, or approve action destinations after incapacity or death?
- How are email recipients, webhook endpoints and script targets proven to be owner-controlled or executor-approved, and what domain/account recovery policy applies if those destinations change hands?
- What cancellation window, dispute process and manual override path exist before any external action becomes irreversible?
